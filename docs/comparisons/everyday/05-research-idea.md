# 研究人员：讨论一个刚冒出来的想法，找到第一步实验

[返回场景列表](../README.md) · [完整调用记录](data/05-research-idea.json)

## 用户问题

我有个早期想法：两个Agent先各自回答，只有答案不一致时才让它们互相看对方的理由，这样可能比每题都讨论更省调用。现有代码已经支持独立回答和两轮讨论，还没做过比较。先别按能不能发论文来评判，帮我判断这个想法具体可能解决什么问题，最容易失败在哪里，以及我明天能跑的一个小实验。

<p>这个想法值得先做小实验验证，核心价值不在“省调用”本身，而在于它把讨论预算集中到真正有分歧的题目上。下面按你的三个问题拆开说。</p>
<h2>1. 具体可能解决什么问题</h2>
<p><strong>主要问题：讨论成本与讨论收益不匹配。</strong> 现在每题都跑两轮讨论，但很多题两个 Agent 初始答案一致，讨论大概率只是互相确认，收益低。你的方案把讨论触发条件设为“答案不一致”，相当于一个免费的置信度代理：一致 ≈ 高置信，不一致 ≈ 需要协商。</p>
<p><strong>次要问题：讨论引入的噪声。</strong> 两轮讨论有时会让原本正确的 Agent 被说服改错（尤其当两个 Agent 能力相近、理由风格不同时）。只在分歧时讨论，能减少“一致但被讨论带偏”的情况。</p>
<p><strong>还有一个隐性收益：</strong> 分歧率本身是个可观测指标。你可以顺带统计不同题型/难度下的分歧率，判断哪些场景值得上讨论、哪些直接单 Agent 就够。</p>
<h2>2. 最容易失败在哪里</h2>
<p>按风险从高到低：</p>
<ol>
<li><strong>“答案一致”不等于“都对”。</strong> 两个 Agent 可能共享同一个错误（同模型不同 prompt、同训练数据偏差），一致地错。这时省掉讨论就省掉了纠错机会。这是最大的风险，也是实验必须量化的。</li>
<li><strong>答案格式不一致导致假分歧。</strong> 数值题 <code>0.5</code> vs <code>1/2</code>、选择题 <code>A</code> vs <code>A.</code>、开放题措辞不同但语义相同——这些会被误判为分歧，触发不必要的讨论，省调用效果打折。需要先做答案归一化。</li>
<li><strong>分歧题上两轮讨论本身不够。</strong> 如果分歧题恰好是难题，两轮讨论可能也收敛不了，你的方案在“该讨论的题”上并没有比基线更强，只是没更差。</li>
<li><strong>触发阈值太粗。</strong> 二值“一致/不一致”丢掉了信息。可以后续考虑用答案相似度或 Agent 自报置信度做更细的触发，但第一版先别加。</li>
</ol>
<h2>3. 明天能跑的小实验</h2>
<p>目标：验证“只在分歧时讨论”相对“每题都讨论”和“完全不讨论”的取舍。用你现有代码，加一个路由分支即可。</p>
<p><strong>数据：</strong> 100–200 题，选你已有评测集里答案可自动判定的部分（选择题或数值题最省事）。如果有多难度分层，每层都采一些。</p>
<p><strong>三个条件，同一批题：</strong></p>
<ul>
<li>A：独立回答，不讨论（下界，省调用但无纠错）</li>
<li>B：每题两轮讨论（你现在的基线）</li>
<li>C：你的方案——先独立回答，一致则直接采用，不一致才跑两轮讨论</li>
</ul>
<p><strong>记录指标：</strong></p>
<ul>
<li>准确率（A/B/C 各自）</li>
<li>总 LLM 调用次数（C 相对 B 省了多少）</li>
<li>分歧率（C 里触发讨论的比例）</li>
<li><strong>关键诊断：一致但错误的题数</strong>（C 相对 A 没纠回来的部分）——这直接量化风险 1</li>
<li>分歧题上 C 的准确率 vs B 在同样这些题上的准确率（讨论有没有用）</li>
</ul>
<p><strong>判读标准（提前定好，避免事后找理由）：</strong></p>
<ul>
<li>若 C 准确率 ≥ B − 1~2 个点，且调用数明显下降 → 想法成立，值得继续</li>
<li>若 C 明显低于 B，看差距是否集中在“一致但错”的题上 → 说明需要更细的触发信号（置信度/相似度），而不是放弃想法</li>
<li>若分歧率极低（比如 &lt;10%）→ 说明两个 Agent 太同质，讨论本身价值就有限，先换 Agent 多样性再谈路由</li>
</ul>
<p><strong>实现上注意两点：</strong> 先做答案归一化再判一致；把“一致但错”的题单独存下来人工看几条，判断是共享偏差还是归一化漏判。</p>
<p>这个实验一天能跑完，而且不管结果正负都能告诉你下一步该调触发信号还是调 Agent 多样性。</p>

</td><td valign="top">
<p>这种方法专门解决了“讨论资源被用于分歧问题”的问题：如果逐一讨论每个问题，那么讨论资源就会被用于那些本来就会被讨论的问题；而先独立回答，只有在出现分歧时才进行讨论，这样就能让讨论资源集中在那些存在实际差异的问题上。其潜在好处有两点：首先，通话总数减少；其次，存在分歧的样本的准确率接近或超过所有讨论的准确率。不过，这种方法可能失败的地方有：答案上的分歧并不一定能通过讨论来纠正；许多分歧情况下，双方都错了，或者一方错了但没有足够的理由来说服另一方。讨论之后，原始答案可能保持不变，甚至正确答案也可能被错误表述。此外，用于判断“答案分歧”的标准（精确匹配或标准化匹配）直接影响了触发讨论的频率及相关成本。如果标准过于严格，讨论就变得没有必要；如果过于宽松，一些本应被讨论的样本就会被忽略。</p>
<p>明天就可以进行一个简单的实验：</p>
<ol>
<li>选择一个已经标注了答案的小数据集，比如100–300个问题，保持相同的模型和提示。</li>
<li>进行三种场景测试：A——只有独立回答（使用第一个智能体或任何固定智能体）；B——完整的两轮讨论；C——采用你的方法：先独立回答，只有在出现分歧时才进行讨论，没有分歧则采用正确答案。</li>
<li>记录每个问题的结果：两个智能体的初始答案是否相同，在场景C中是否触发了讨论，A/B/C的最终答案是否正确，以及总通话数。</li>
<li>关注三个指标：与场景B相比，节省的通话比例；场景C与B之间的准确率差异；在“最初有分歧”的子集中，讨论前后的准确率变化（准确率的恢复程度，以及正确答案被错误表述的次数）。</li>
<li>对于答案匹配，先进行一层标准化处理（去除空格、标准化大小写、标准化数字格式），并报告精确匹配和标准化匹配的率，以避免因使用标准而导致的结论偏差。</li>
</ol>
<p>判断标准可以提前确定：如果场景C的通话数明显低于场景B，且准确率下降在可接受范围内（例如不超过1–2个百分点），那么这种方法值得继续实施。如果讨论对存在分歧的子集的净收益接近零或为负，那么问题在于是否通过讨论能够纠正分歧；此时需要改变讨论策略，而不是继续节省通话数。</p>
