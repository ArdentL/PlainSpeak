# 10 个 Agent 常用场景：DeepSeek 原版 vs skill + 回译

**每页左边是未经 PlainSpeak 修改的 DeepSeek，右边是启用清晰表达规则后再本地回译的结果。两边展示完整输出，保留变差和部分回退的案例。**

这轮结果：9/10 组加入 skill 后篇幅缩短；9/10 组最终稿比原版短。但回译后的 10/10 组都比各自的 skill 原稿更长。总字符数从原版 16797 降至 skill 原稿 7953，回译后为 8754。这批案例中的篇幅收益主要出现在 skill 阶段；回译还出现了术语误译、否定含义变化和冗长表达。字符减少不等于质量提高。

这不是效果保证，也没有用一个总分掩盖失败。[实验设计](05-experiment-design.md)中的“置信区间跨零”被改成“置信区间为零”；[交接说明](10-handoff.md)被改成“切换说明”。[环境排错](02-environment.md)有两块正文因行内代码检查失败而保留 skill 原稿。

## 测试条件

- 执行日期：2026-11-10。十个固定的中文虚构场景，每个场景两个全新对话，共 20 次实际 DeepSeek API 调用。没有质量重抽或人工改写。
- 请求模型 `deepseek-v4-flash`，提供方实际返回的模型标识为 `deepseek-flash`；左右两边一致。`temperature=0`、`thinking.type=disabled`、`max_tokens=8192`，全部以 `stop` 结束。没有提供工具，也没有执行生成答案中的命令。
- 左侧不提供自定义 system 消息，只发送页面展示的用户问题；它不是经过我们故意写差的稿子，也不是当前 Codex 模拟的 DeepSeek。
- 右侧在 system 消息中加入 PlainSpeak 0.7.0 实际使用的 `CLEAR_WRITING` 清晰表达规则，再生成独立回答。这就是当前 Harness 插件自动注入的 skill 核心规则，不依赖模型主动调用 skill 工具；完整文本在 [protocol.json](data/protocol.json)。
- 本地回译使用腾讯 `Hy-MT2-1.8B-Q4_K_M`，固定 SHA-256 为 `dc5f44fcf1fa496ee7ad725982c0c8c553a4de00259b53af84c4b89fb0c06699`；运行项目未修改的 `plainspeak.core.rewrite`，默认 750 字符分段，中文 → 英文 → 中文，保留代码与现有保护回退。
- **本页走 core/CLI 的整篇 Markdown 分段路径，`context=""`。它不是 Harness 前端按 DOM 段落收集相邻上下文的那条路径，也不是完整的 Agent 工具执行轨迹。** 示例只代表上述实际配置。普通数字按当前产品策略不做一致性保护。
- 右侧的写作规则和回译同时参与变化，不能只凭左右两份独立生成的答案认定差异由哪一步造成。因此另外保留 skill 原稿，用来查看回译前后的实际变化；不做“平均提升多少分”的推断。

## 如何核对或复现

1. 打开任一场景的 `data/*.json`，核对用户问题、完整 system 消息、生成模型与参数、响应停止原因和用量。左侧没有 system 消息，右侧只多出已公开的写作规则。
2. 用自己的 DeepSeek 凭据分别发送相同的两组消息；不要复用上一条对话历史。协议、问题清单与每个输出的 SHA-256 在本目录的数据文件里。
3. 把新生成的 skill 原稿保存为 UTF-8 Markdown，按项目正常安装步骤准备默认模型，然后运行：

   ```powershell
   plainspeak rewrite skill-answer.md --language zh-CN --pivot en --output rewritten.md
   ```

   命令参数以当前版本 CLI 帮助为准；本轮实际调用的是同一核心库的 `rewrite(..., language='zh-CN', pivot='en', chunk_size=750)`。原始代码块没有交给翻译模型。逐次英文中转与返回中文已经保存在各场景证据文件。
4. 阅读每页“观察”：区分原模型/skill 原稿已有的问题与回译新引入的问题，不用新输出覆盖此轮原始结果。

20 次调用合计提供方报告：输入 3394 tokens，输出 13710 tokens，总计 17104 tokens。用量只包括 DeepSeek；本地模型耗时另存各场景记录。这不是跨模型或跨机器速度比较。
