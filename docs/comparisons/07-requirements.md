# 确认桌面插件第一版需要做什么

[返回场景列表](README.md) · [调用记录](data/07-requirements.json)

## 用户问题

我想做一个桌面插件：回答太绕的时候自动显示更好读的版本，支持开关，数据最好留在本地。先只支持一个聊天客户端。你现在需要问我哪些问题？请选真正影响第一版实现的点，别一次丢一大堆问题。

## 回答对比

左侧是未加写作规则的 DeepSeek 回答；右侧是在相同问题下加入清晰表达规则后生成、再经过本地回译的回答。两份回答均未人工修改。

<p>先问最关键的 5 个，够定第一版骨架：</p>
<ol>
<li>
<p><strong>哪个聊天客户端？</strong><br />
是网页版（如 WhatsApp Web / Slack Web / Discord Web）还是原生桌面应用？这决定我是做浏览器扩展、桌面壳注入，还是读本地数据库/API。</p>
</li>
<li>
<p><strong>“回答太绕”怎么判定？</strong><br />
第一版你希望是：手动触发（选中/快捷键）→ 显示更好读版本，还是自动检测长/复杂回答后提示？自动判定会显著增加复杂度。</p>
</li>
<li>
<p><strong>“更好读的版本”由谁生成？</strong><br />
本地小模型、调用云端 API、还是规则化改写（分段/列点/去冗余）？这直接影响“数据留在本地”的可行性和实现量。</p>
</li>
<li>
<p><strong>显示形态？</strong><br />
是在原消息旁内联替换/展开，还是侧边栏/浮层显示？是否需要保留原文对照？</p>
</li>
<li>
<p><strong>开关粒度？</strong><br />
只要一个总开关，还是按会话/按消息临时开关？第一版建议总开关 + 单条手动触发，你确认下是否接受。</p>
</li>
</ol>
<p>你回答这 5 个后，我再问第二轮（存储、权限、失败降级），不会一次堆太多。</p>

</td><td valign="top">
<p>首先，提出5个会直接影响第一个版本结构的问题：</p>
<ol>
<li>
<p><strong>目标聊天客户端是什么？它是否有可用的插件或扩展接口？</strong><br />
这决定了第一个版本是以正式插件形式呈现，还是以桌面浮动窗口形式呈现，或者通过屏幕阅读器/剪贴板功能来呈现。如果客户端没有扩展接口，那么实现复杂度和合规风险都会有很大差异。</p>
</li>
<li>
<p><strong>导致“难以理解”状态的触发方式是什么：用户手动激活、快捷键，还是自动判断？</strong><br />
对于第一个版本，建议采用手动激活方式。自动判断则需要明确界定“复杂性”的标准，这可能会无谓地扩大功能范围。这一选择直接决定了是否需要对聊天内容进行实时监控。</p>
</li>
<li>
<p><strong>易于理解的版本应该由本地规则生成，还是使用本地模型？</strong><br />
基于规则的版本只能进行分割、去重和高亮显示；而本地模型则能修改和压缩内容。这两种方式都会对安装包的大小、延迟、硬件要求以及隐私问题产生重大影响。</p>
</li>
<li>
<p><strong>“数据本地存储”具体意味着什么：无需互联网连接，无需磁盘存储，还是仅存储在设备本身？</strong><br />
如果需要完全离线功能，则无法使用云API。如果允许本地存储，还需要决定原始文本、处理后的结果以及设置信息是否应被保存。</p>
</li>
<li>
<p><strong>控制所需的精度如何：仅控制整体功能开关，还是同时控制自动激活和本地存储？</strong><br />
第一个版本必须明确说明：关闭开关后是否停止读取聊天内容，以及存储的数据是否会被删除。这会影响权限设计与用户信任度。</p>
</li>
</ol>
<p>通过回答这5个问题，我可以确定第一个版本的范围及最低验证方式。</p>
