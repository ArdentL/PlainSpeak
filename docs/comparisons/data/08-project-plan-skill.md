# 两周本地文本改写插件：分工与交付计划

## 先定第一版边界

第一版只做四件事：**自动处理、原文对照、开关、本地记录**。云同步不做。插件通过聊天客户端的公开插件接口接入，改写由你们已有的本地小翻译模型完成。

建议把“自动处理”定义为：用户在客户端里选中文本或触发插件后，插件自动调用本地模型改写，并把结果回填或展示。不要在第一版做全自动监听所有输入，否则接口兼容和误触发会吃掉大量时间。

## 分工

按两人各自更熟的方向分，下面给一个默认方案，你们可以按实际技能对调：

**A：插件与客户端集成**
- 对接聊天客户端公开插件接口，完成插件注册、触发入口、结果回填。
- 实现开关状态：插件启用/停用，以及单次处理是否自动执行。
- 处理原文与改写结果的对照展示。
- 负责端到端联调和客户端侧验收。

**B：本地模型服务与记录**
- 封装本地小翻译模型的调用：输入清洗、改写提示、超时和失败处理。
- 实现本地记录：每次处理的原文、改写结果、时间、是否成功，存本地文件或本地数据库。
- 提供插件调用的本地接口，保证模型不可用时插件能降级提示而不是卡死。
- 负责模型侧和记录侧验收。

**共同**：第一天一起定接口契约（请求字段、返回字段、错误码），之后各自开发，每天一次短同步。

## 时间安排

**第 1 天：定契约和跑通最小链路**
- 一起确定插件调用本地服务的接口格式，以及记录的数据结构。
- A 跑通客户端插件最小示例；B 跑通模型最小调用。
- 验收：A 能在客户端触发一个假改写并回填；B 能对一段文本返回改写结果。

**第 2–4 天：各自完成核心模块**
- A 完成插件入口、开关、原文对照展示。
- B 完成模型封装、超时/失败处理、本地记录写入。
- 验收：单独模块可运行，接口按契约返回。

**第 5–6 天：联调**
- 接通真实模型，跑通“触发→改写→对照展示→写记录”全链路。
- 验收：选 10 段代表性文本，逐段检查改写结果、原文对照是否正确、记录是否完整。

**第 7–8 天：异常与边界**
- 测模型超时、模型返回空、客户端重复触发、开关关闭时不应处理。
- 验收：上述异常都有明确提示或安全降级，不崩溃、不写脏记录。

**第 9–10 天：验收与修缺陷**
- 按下面验收清单逐项过，修阻塞问题。
- 验收：清单全部通过或明确记录未通过项。

**第 11–12 天：缓冲**
- 只修缺陷和补最必要的说明，不加新功能。

**第 13–14 天：交付**
- 整理安装/启动说明、已知限制、记录文件位置。
- 验收：另一台机器按说明能跑起来。

## 验收清单

1. 在客户端中能启用/停用插件，停用后不触发处理。
2. 触发后自动调用本地模型完成改写，结果可见。
3. 原文与改写结果并排或上下对照，能区分两者。
4. 每次成功处理都写入本地记录，字段完整、可读回。
5. 模型超时或失败时有提示，不卡死客户端，不产生错误记录。
6. 连续多次触发不串结果、不重复写记录。
7. 按交付说明在干净环境能启动并完成一次完整处理。

## 时间不够时砍什么

按以下顺序砍，越往后越先砍：

1. **先砍对照展示的样式**：保留纯文本对照即可，不做高亮、 diff、折叠。
2. **再砍记录的丰富度**：只保留原文、结果、时间、成功/失败，不做搜索、导出、清理界面。
3. **再砍自动处理的触发方式**：从“选中即处理”退到“手动点一次处理”，开关仍保留。
4. **最后砍模型侧的高级处理**：不做长文本分段、不做多轮改写，只保证单段文本可用。

**不要砍**：开关、原文对照的基本能力、本地记录的基本写入、失败提示。这四项是第一版的核心，砍掉就不算完成。

如果到第 10 天联调仍未跑通，应停止加功能，把剩余时间全部用于打通最小链路和写清已知限制，而不是继续铺模块。
